## Design

### 扁平化存储方案

```
输入: "adj. 复杂的; 难懂的 n. 情结; 建筑"
                    │
                    ▼
         ┌─ 多词性拆解 ─┐
         │              │
    pos="adj.; n."   chinese="复杂的; 难懂的; 情结; 建筑"
         │              │
         ▼              ▼
    存入 words.pos   存入 words.chinese
```

### 分割算法细节

```
meaning_raw = "adj. 复杂的; 难懂的; 复合的 n. 情结; 建筑"

扫描过程：
  ┌── 匹配 adj. ──→ 提取 pos="adj.", chinese="复杂的; 难懂的; 复合的"
  │     剩余: " n. 情结; 建筑"
  │
  ├── 匹配 n. ──→ 提取 pos="n.", chinese="情结; 建筑"
  │     剩余: ""
  │
  └── 输出: pos="adj.; n.", chinese="复杂的; 难懂的; 复合的; 情结; 建筑"
```

对于 `&` 连接的情况：
```
meaning_raw = "vt. & vi. 计算; 估计"

扫描过程：
  ┌── 匹配 vt. ─→ 提取 pos="vt.", chinese="" （& 前无中文）
  │   遇到 "&"  → 跳过，继续
  │
  ├── 匹配 vi. ─→ 提取 pos="vi.", chinese="计算; 估计"
  │
  └── 输出: pos="vt.; vi.", chinese="; 计算; 估计" → 清理后 "计算; 估计"
```

### 断字正则增强

当前 `_BREAK_FIX_RE` 只匹配前缀 ≤3 字母，但 #1257 `su rvey`(前缀 su=2) 和 #1266 `sw ing`(前缀 sw=2) 应该能命中才对。需要诊断为什么没匹配——可能是后缀部分包含了非纯字母内容（音标残留）。

**调整方案**：放宽断字正则的后缀匹配条件，允许后缀中包含 `[` 等音标字符。

### 不改动的部分

- **数据库 schema**：pos 和 chinese 都是 TEXT，天然支持多值
- **app.py 导入逻辑**：已经直接映射字段名
- **前端模板**：先保证数据正确，展示优化作为后续事项

## Trade-offs

| 选择 | 优点 | 缺点 |
|------|------|------|
| 扁平化存储 | 改动最小、零 schema 变更 | 查询特定词性需字符串匹配 |
| JSON/子表存储 | 查询灵活、结构清晰 | 改动大、需迁移 |

选择扁平化的理由：这是一个单词学习 app，不需要按词性做复杂查询，展示时简单拆分即可。
