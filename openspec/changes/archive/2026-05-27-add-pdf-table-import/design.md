## Context

`pdf_parser.py` 当前用 `pdfplumber.extract_text()` 按行扫描，主正则 `_ENTRY_RE` 强制要求每行以 `\d+\.` 开头。这套方案是为编号词表（如雅思 3500 PDF）量身设计的，覆盖率约 98%。

但 `extract_text()` 把表格 PDF 的每一行 cell 用空格拼接成一行文本：原本的 `["alarming rate of loss", "plight"]` 会变成 `"alarming rate of loss plight"`，没有任何分隔标记，且行首没有编号——结果就是 `_ENTRY_RE` 全部失配，整个 PDF 在用户眼里"导入失败"。

`pdfplumber` 自带 `page.extract_tables()`，基于"线条 + 字符盒子"识别带边框表格，返回 `list[list[list[str]]]`（页 → 表 → 行 → cell），结构与 Excel 路径的 `parse_table_raw` 输出**天然同构**。这是双路径分发设计的基础。

同义词学习功能刚上线（`flashcard_synonym.html` + `/learn/synonym/*` 路由），其前置条件是 `words.synonyms` 字段非空。表格 PDF 词库恰好是同义词学习的最佳数据源，需要在导入时就把 B 列写入 `synonyms` 字段。

## Goals / Non-Goals

**Goals:**
- 让表格 PDF（带边框、可选中文字层）能像 Excel 一样走完整导入流程
- 同义词词库（英文-英文双列）开箱即用，导入即可立刻使用同义词学习
- 保持现有编号词表 PDF 路径 100% 不变，零回归
- 错误提示能让用户知道"扫描图 PDF 不支持，请预处理"，而不是给出空的预览页
- 不引入新依赖、不增加桌面 app 包体积

**Non-Goals:**
- 扫描图 PDF 的 OCR 识别（隐私 + 体积 + 准确率三重劣势，详见 Decisions D5）
- 无边框纯空白对齐表格的识别（pdfplumber 也搞不定，超出范围）
- 按页/按章节自动拆分为多个词库（用户明确选择"全部合并"）
- 表格内嵌图片的提取或保留（图片不影响文字层抽取，且 app 内无展示位）

## Decisions

### D1：双路径分发——先表格、后编号词表

**决策**：上传 PDF 后，先对**所有页**调用 `extract_tables()`。若任何一页抽到至少一个有效表格（≥2 行 ≥2 列），走表格路径；否则降级到现有 `_ENTRY_RE` 路径。

**为什么**：
- 表格 PDF 走 `_ENTRY_RE` 必失败（行首没有 `\d+\.`）
- 编号词表 PDF 走 `extract_tables()` 必返回空（没有边框）
- 两者互斥，按"试一下表格、不行再回退"的顺序最稳

**备选方案**：
- 让用户上传时勾选 PDF 类型 → 多一步操作，体验差
- 用文件名/内容启发式判断 → 不可靠

### D2：表格抽取的鲁棒性策略

**决策**：表格抽取后做三层清洗：

1. **跨页合并**：所有页的所有表格行 flatten 到同一个 `rows` 列表
2. **结构对齐**：以最常见的列数为基准，列数不一致的行（合并单元格产物）整行剔除
3. **非数据行剔除**：
   - 单 cell 行（"C4 Test 1" 这种横跨表头的标题）→ 跳过
   - 列名匹配 `{"文章", "题目", "Word", "Synonym", "单词", "释义"}` 等 → 标记为表头，由 `looks_like_header` 判定后跳过

**为什么**：用户选择"全部合并到一个词库 + 自动跳过非数据行"，这三层是最小必要清洗。

### D3：同义词模式——B 列双写到 chinese 与 synonyms

**决策**：列映射页新增一个单选「导入模式」：
- **标准模式**：`B 列 → chinese`（与现状一致）
- **同义词模式**：`B 列 → chinese AND synonyms`（同时写两个字段）

默认值由智能判断决定：B 列中文字符占比 < 10% 时默认勾选"同义词模式"，否则默认"标准模式"。用户可随时手动切换。

**为什么 B 列要双写而不是仅写 synonyms**：
- 仅写 synonyms：`chinese` 为空 → 翻卡学习背面看不到东西、4 选 1 测试无法生成、所有依赖 `chinese` 字段的功能失效
- 双写：所有现有功能照常工作，同义词学习也直接可用，零功能损失
- 雅思学习的本质是"看到 alarming rate of loss 能想到 plight"，英文同义词在功能上**就是**它的"释义"

**实现位置**：`apply_mapping(rows, ..., import_mode='standard'|'synonym')`，仅一行差异 `synonyms = chinese if import_mode=='synonym' else ''`。

### D4：放宽中文列识别——按"非英文列"兜底

**决策**：`guess_columns` 中，当所有列的中文占比都 < 0.2 时，不再返回 `chinese_col=-1`，而是退化为"挑一个 ASCII 占比 > 0.5 但低于 english_col 的列"作为释义列候选。

**为什么**：英文同义词词库（B 列也是英文）现有逻辑必然返回 `chinese_col=-1`，导致用户在列映射页看到下拉框未选，点"继续"被后端拒绝。退化策略让英文-英文表格也能被自动猜中。

**保护机制**：英文列优先级始终最高，绝不会出现两列都被选作"英文列"或都被选作"释义列"的情况。

### D5：扫描图 PDF——明确拒绝 + 引导提示，不做 OCR

**决策**：上传 PDF 后立即检查 `pdf.pages[0].chars` 是否为空（或全部页面字符总数 < 10）。若是扫描图 PDF，返回错误：

> 这个 PDF 看起来是扫描图，无法直接读取文字。请先用 WPS / Adobe Acrobat 等工具将其转换为可选中文字的 PDF（或直接导出为 Excel），再上传。

**不做 OCR 的理由（评估三种方案后否决）**：
- 本地 Tesseract：依赖体积 ~300MB+，桌面 app 膨胀 10 倍；中英混排表格准确率 70-85%
- 云端 OCR API：需要联网 + API key，破坏 README 强调的"数据不出本机"卖点
- 用户预处理：成本最低，且 WPS / Adobe / 在线工具普及度高，3 分钟搞定

### D6：路由层零侵入——复用 Excel 的列映射前端

**决策**：表格 PDF 抽取出 `rows` 后，写入与 Excel 完全相同的 `_save_excel_raw(...)` 临时文件，跳转到 `/import/excel_mapping`，复用 `import_excel_mapping.html`。导入模式开关在该模板中新增。

**为什么**：避免维护两套近似但不同的 UI；用户无论上传表格 PDF 还是 Excel，看到的列映射体验完全一致；后续若再有第三种结构化导入源（如 Numbers 文件），也能直接接入这条流。

### D7：智能判断同义词模式默认值

**决策**：在 `guess_columns` 返回值中新增 `suggested_mode: 'standard'|'synonym'` 字段。判定规则：

```
释义列中文字符占比 < 10%  → suggested_mode = 'synonym'
否则                       → suggested_mode = 'standard'
```

UI 根据该字段渲染单选默认勾选。

**为什么 < 10% 不是 == 0**：表格 PDF 中偶尔会混入个别中文标点或注释字符，绝对零中文太严格。

## Risks / Trade-offs

**[R1] pdfplumber 表格识别失败**：某些 PDF 表格可能没有边框，或边框是图片不是矢量线。
→ Mitigation：双路径设计本身就是兜底——表格抽不到就回退到 `_ENTRY_RE`。最坏情况退化为现状。

**[R2] 跨页合并造成的数据污染**：多页表格如果各页结构不同（列数不一致），合并后会乱列。
→ Mitigation：D2 的"结构对齐"——以最常见列数为基准剔除异常行；预览页让用户看到结果再决定是否导入。

**[R3] 智能判断同义词模式判错**：B 列偶尔含一两个中文字（如人名翻译）可能让用户期望"标准模式"却被默认到"同义词模式"。
→ Mitigation：单选可手动切换；UI 文案明确标注"已根据内容自动判断，可手动调整"。

**[R4] `extract_tables()` 性能**：大型多页 PDF 抽表格可能比 `extract_text()` 慢 3-5 倍。
→ Mitigation：仅在 PDF 类型分发那一步触发；用户已经习惯导入需要等待，且本地处理无网络成本。如果未来发现明显卡顿，可加入 page 数上限或进度提示。

**[R5] 与现有同义词字段语义冲突**：同义词模式下 `synonyms = "plight"`（仅一个词），但词库管理页的同义词搜索/编辑预期 `synonyms = "plight, mate, buddy"`（逗号分隔多个）。
→ Mitigation：单同义词形态与多同义词形态在 UI 上展示一致（都是直接渲染字符串），不需要特殊处理；用户后续可在词库管理页编辑增加更多同义词。

**[R6] 用户上传混合 PDF（既有编号词表也有表格）**：极端情况下，PDF 第一页是编号词表第二页是表格。
→ Mitigation：双路径互斥，先尝试表格——若表格命中，整个 PDF 走表格流程，编号词表那部分会丢失。预期用户不会有这种 PDF；若真出现，错误提示让用户拆分文件后分别上传。
