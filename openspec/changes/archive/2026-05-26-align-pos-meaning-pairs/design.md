# Design: 对齐词性与释义

## 数据流变更

```
┌────────────────────────────────────────────────────────────────────┐
│                  解析与展示数据流（新版）                              │
└────────────────────────────────────────────────────────────────────┘

  PDF 多行原始数据
       │
       ▼
  ┌─────────────────────────────────┐
  │ 行预处理                         │
  │ - 断字修复 (BREAK_FIX_RE)        │
  │ - 字符间空格修复 (新增)           │
  └─────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────┐
  │ 多行合并                          │
  │ - 序号行                         │
  │ - 续行类型 A: 音标残尾 + pos. + 释义│
  │ - 续行类型 B: pos. + 释义         │
  │ - 续行类型 C: 美 [音标] + pos.+释义│
  └─────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────┐
  │ 提取 list[(pos, chi)]            │
  │ 内部用结构化列表，不再是字符串拼接   │
  └─────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────┐
  │ 序列化为模型 C 字符串              │

  │ pos     = "n.; vt." (兼容字段)    │
  └─────────────────────────────────┘
       │
       ▼ 写入数据库
  ┌─────────────────────────────────┐
  │ 模板渲染                          │
  │ chinese.split(' | ') → 多行      │
  └─────────────────────────────────┘
```

## 关键设计决策

### 决策 1: 内部数据结构用 list[(pos, chi)]

**为什么**：解析过程中需要往同一个词性追加释义（多个续行），用列表+字典操作比字符串拼接安全。

```python
# 内部
meanings = [
    ('n.', '学徒，徒弟; 新手'),
    ('vt.', '使…做学徒'),
]

# 序列化
chinese = ' | '.join(f'{pos} {chi}' for pos, chi in meanings)
pos_str = '; '.join(p for p, _ in meanings)
```

### 决策 2: 词性合并规则

```
规则:
  - 同一个 pos_key 出现多次 → 释义用 "; " 追加到同一条目
    pos_key 通过 .replace(' ','').replace('&','').lower() 归一化
  
  - "vt. & vi." → 拆为两个独立条目 (vt., '') 和 (vi., '')
    后续若有释义则填充
```

### 决策 3: 空释义条目的处理

```
忽略规则:
  if not chi.strip():
      # 不加入 meanings 列表
      continue
  
  特例: "vt. & vi." 拆出的两个条目可能初始 chi 都为空
        → 把当前行剩余的释义同时分配给两个 (兜底)
        → 若仍为空，丢弃该词性
```

### 决策 4: PDF 续行识别

```
续行检测规则（在词条主行处理完后向下扫描）:
  停止条件: 遇到下一个序号行 OR 行不匹配任何续行模式

  类型 A（音标残尾 + 词性释义）:
    正则: ^[a-zA-Zəˈˌːɪʊɛɔæɒɑʌəʃʒθðŋ\s'\(\)\.,;]+\]\s*([a-zA-Z]+\.)\s*(.+)$
    示例: "əˈdɪkt (for v.)] vt. 使沉溺"
          "səˈveɪ] vt. 调查；勘测"
    动作: 提取 pos + 释义合并到主条目

  类型 B（纯词性释义）:
    正则: ^([a-zA-Z]+(?:\s*&\s*[a-zA-Z]+)?\.)\s+(.+)$
    示例: "vi. 测量土地"
    动作: 提取 pos + 释义合并

  类型 C（美式音标 + 词性释义）:
    正则: ^美\s*\[[^\]]*\]?\s+(.+)$  (已有)
    示例: "美 [əˈprɛntɪs] vt. 使…做学徒"
    动作: 提取词性释义部分合并

  类型 D（纯音标续行，无释义）:
    正则: 仅含音标字符 + ]
    示例: "əˈproprɪet]"  (appropriate 的美式音标续行)
    动作: 跳过（不影响主条目）
```

### 决策 5: 字符间插空修复

```
问题: PDF 提取出 "v t . 使 沉 溺" — 字符间被插了空格

修复策略（仅在续行处理时应用，避免误伤）:
  1. 用正则替换连续的"单字符+空格"模式
     pattern: r'([a-zA-Z\u4e00-\u9fa5])\s+(?=[a-zA-Z\u4e00-\u9fa5\.])'
     注意: 不能影响正常的英文单词间空格 → 限制为单字符前后

  实际方案（更安全）:
  - 仅在含有 ".]"+"vt." 等特殊模式时尝试压缩
  - 用 lookbehind 确保只压缩"单字符+空格"组合
```

### 决策 6: `(for xxx.)` 词性提取

```
当前行为: "(for adj." 中的 "adj." 被当注释丢弃 → appropriate 没词性

新行为:
  - 识别 (for xxx.) 中的 xxx. → 视为该条目的词性
  - 用法: "appropriate 英 [əˈprəʊprɪət;(for adj. 占用，拨出"
          → 提取出 pos="adj." chi="占用，拨出"
```

## 前端展示

### 模板修改

各模板中渲染 `word.chinese` 的地方改为：

```jinja2
{# 旧 #}
<div class="meaning">{{ word.chinese }}</div>

{# 新 #}
<div class="meanings">
  {% for line in word.chinese.split(' | ') %}
    <div class="meaning-line">{{ line }}</div>
  {% endfor %}
</div>
```

### CSS 样式（最小化）

```css
.meanings .meaning-line {
  margin-bottom: 4px;
  line-height: 1.6;
}
```

## 不在范围内

- 不引入 JSON 字段（保持 schema 不变）
- 不修改测试/听写出题逻辑（按词性出题是后续优化）
- 不重做 import preview（自动兼容字符串展示）
